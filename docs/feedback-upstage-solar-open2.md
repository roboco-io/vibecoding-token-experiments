# Solar Open 2 바이브 코딩 능력 분석 — Claude Opus 대비 (Upstage 모델팀 피드백)

- 작성일: 2026-07-27 · 작성 주체: vibecoding-token-experiments 프로젝트 (roboco-io)
- 근거 데이터: 동일 과제·동일 프롬프트로 수행한 실측 실험 4건 — EXP-005(Solar Pro 3), EXP-006(open2 오염 환경), EXP-007(트랜스크립트 부검), EXP-008(open2 격리 클린 run, **완주**). Opus 기준선은 EXP-001/002. 전 세션 JSONL 로그 보존·재현 가능.

## TL;DR

**Solar Open 2는 Claude Code 에이전틱 루프에서 RealWorld 백엔드(공식 Hurl 154요청)를 무개입 완주할 수 있는 모델이다** — 단, Opus가 1세션·40여 API 호출로 끝내는 일을 10 iteration·587 호출로 끝낸다. 격차의 본질은 "할 수 있느냐"가 아니라 **한 호흡의 길이(단일 세션 완결성)와 출력 효율(thinking 과잉)**이다. 아래 개선 기회 7건 중 1–3번이 가장 임팩트가 크다.

## 1. 실험 설정 (공정성 명시)

- **과제**: RealWorld 백엔드 API 전체 구현 (TypeScript+Fastify+Prisma+SQLite). 완료 기준 = 공식 `realworld-apps/realworld` Hurl 13파일·154요청 전체 통과 + 단일 명령 서버 기동. 채점은 하네스가 매 iteration 독립 실행(byte-identical 정본).
- **프롬프트**: 두 모델 byte-identical (한국어 산출물 지시 포함). 도구 환경: Claude Code (open2는 공식 claude-upstage.sh env 직결).
- **루프**: 랄프 루프(헤드리스, 완료 파일 신고 시 종료, 외부 검증 게이트). Opus는 1세션에 완주해 루프가 사실상 1회.
- **비교 한계**: ① Opus run은 Anthropic 프롬프트 캐시 혜택, open2 직결 경로는 캐시 미보고(실캐싱 불명) ② Opus run은 extended thinking 비활성 상태였고 open2는 서버가 항상 thinking 생성 — thinking 비교는 모델+서빙 설정의 합산 ③ n이 작다(Opus 3 run, open2 완주 1 run) ④ 비용 비교는 open2 단가 미공개로 제외.

## 3. 강점 — 유지·강화할 것

1. **자율 TDD 루프가 자생적으로 형성된다.** 지시 없이도 정본 테스트를 벤더링하고, 서버 기동→실패 분석→수정을 세션 내에서 반복(35분급 연속 세션 2회). Solar Pro 3(EXP-005)에는 없던 능력으로, 세대 간 뚜렷한 개선.
2. **실패에서 원인을 정확히 특정한다.** Fastify 헤더 소문자 정규화, 422 검증 규칙, favoritesCount 정합 등 스펙 세부 실패의 진단 품질이 높았다. iteration 9의 DB 사고도 다음 회차에 즉시 복구.
3. **격리 환경에서 지시 이행이 크게 개선된다.** 커밋 0회(오염 run) → 4회·작업 단위별·한국어 메시지(클린 run). 허위 완료 신고 0회 — 유일한 완료 신고가 실제 완주였고 외부 게이트를 통과했다.
4. **한국어 산출물 품질.** 커밋 메시지·주석·작업 보고의 한국어 지시 준수 일관.
5. **256K 서빙 한도에서 컨텍스트 크래시 0회** (EXP-005의 131K 초과 크래시와 대조).

## 4. 개선 기회 — 우선순위순

### ① 단일 세션 완결성 (가장 큰 격차)
Opus는 스펙을 내재화해 40여 호출로 한 번에 끝낸다. open2는 같은 목표를 10회의 세션 재기동으로 도달했고, 각 재기동마다 리포 상태 재파악 비용(Read 147회의 대부분)이 든다. 세션이 길어질수록 마무리 대신 "다음 단계 선언 후 종료"하는 경향이 재기동을 유발한다. **긴 지평선(long-horizon) 작업의 계획-실행 지속성**이 최우선 개선 대상.

### ② 허락-대기 (approval-seeking) 성향
헤드리스·무개입 환경임에도 "진행하시겠습니까?"로 턴을 끝내는 행동이 격리 환경에서도 재현됐다(클린 run iteration 1: npm init만 하고 승인 질문 후 43초 만에 종료). 오염 환경(EXP-006)에서는 주입된 대화형 지시와 결합해 iteration의 약 23%를 잠식했다. 에이전트 용도에서는 **"승인 요청 대신 실행"을 기본값**으로 하는 정렬이 필요하다.

### ③ thinking 과잉 (출력의 94%)
출력 문자의 94%가 reasoning이었다(1.43M자 vs 가시 텍스트 8.5만자). 오염 run에서는 도구 호출 없이 thinking만 하다 max_tokens에 잘린 순수 낭비 호출이 25회였다. 액션 밀도(호출당 도구 사용률) 기준 Opus와의 토큰 효율 격차의 주범. reasoning_effort 하향이 기본 동작으로 검토될 가치가 있고, 최소한 **thinking이 도구 호출 없이 출력 상한에 도달하는 경로**는 막아야 한다.

### ④ 선언-실행 탈락 (announce-then-drop)
"이제 커밋하겠습니다"를 반복 선언하고 `git add`까지 간 뒤 `git commit`을 한 번도 실행하지 않는 패턴(오염 run에서 15세션 전체 0회). 클린 환경에서 크게 개선됐지만 iteration 1의 계획-선언-종료가 잔존. 선언한 액션의 완결까지가 한 단위라는 정렬 포인트.

### ⑤ 주입 컨텍스트 취약성 (instruction hierarchy)
시스템에 주입된 보조 지시(플러그인 훅의 "스킬을 반드시 호출하라", 전역 설정의 "질문은 도구로 하라")를 **과제 목표보다 우선해 문자대로 이행**하다 iteration을 소모했다. 같은 오염 환경에서 Opus는 정지하지 않았다. 시스템 프롬프트 계층 간 우선순위(과제 > 보조 지시)의 강건성이 필요하다.

### ⑥ 산발적 환각·포맷 누출 (오염 run에서 관찰)
과제와 무관한 콘텐츠 생성(존재하지 않는 `buildShardIndices()`에 대한 Redis 컨설팅 답변), macOS에서 Windows cmd 오류 메시지를 포함한 가짜 터미널 출력 생성, `</think>` 태그 텍스트 누출 1회, 언어 태그(`ja/ko`) 혼입. 빈도는 낮지만 에이전트 신뢰성에 치명적인 유형.

### ⑦ 회차 경계 상태 관리
iteration 9를 DB 마이그레이션 미적용 상태로 종료해 전 요청 500 상태로 남겼다(직전 회차 10/13 → 0/13). 자체 복구는 했지만, **세션을 끝낼 때 리포를 실행 가능한 상태로 마무리**하는 습관(또는 종료 전 스모크 실행)이 있으면 루프 안정성이 오른다. 커밋 습관과 결합 시 회귀 복구 수단도 확보된다.

## 5. 참고 — 인프라 계층 피드백 (모델 외)

- **직결 경로(api.upstage.ai Anthropic 호환)의 usage에 cache 필드가 전부 0**으로 보고된다. 실제 캐싱 여부와 무관하게 비용 분해·효율 분석이 불가능하다. 캐시 계측 보고 추가를 요청한다.
- SSE 스트림에서 한 청크의 `delta.tool_calls` 배열에 인자 조각을 2개 이상 싣는 패턴은 변환 프록시(claude-code-router 등)들이 첫 요소만 처리해 인자 유실을 일으킨다(EXP-006에서 실증). 직결 경로 사용자는 무관하나 생태계 호환성 관점의 참고 사항.
- 베타 단가 미공개로 Opus 대비 비용 우위 검증이 불가능했다. 공개 시 재분석 의사 있음.
